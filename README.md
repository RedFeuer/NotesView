# NotesView

Android-приложение для создания, просмотра и редактирования заметок.

Основной интерфейс приложения реализован на **Android Views и Fragments**. Проект построен с разделением на `presentation`, `domain` и `data` слои, использует **Room** для локального хранения данных и **Dagger 2** для внедрения зависимостей.

Одна из основных особенностей приложения — собственный `ViewGroup` для отображения заметок в виде анимированных стеков. Для эффективного обновления списка используется `RecyclerView` вместе с `DiffUtil` и payload-обновлениями, позволяющими перерисовывать только изменившуюся заметку внутри стека.

Интерфейс адаптирован под разные ориентации устройства: в портретном режиме список и редактор открываются последовательно, а в альбомном используется двухпанельный layout со списком заметок слева и редактором справа.

## Возможности приложения

- создание и редактирование заметок;
- просмотр списка заметок;
- поиск заметок;
- группировка заметок по дате;
- отдельное отображение важных заметок;
- объединение обычных заметок в визуальные стеки;
- раскрытие и сворачивание стеков с анимацией;
- отметка заметки прочитанной по долгому нажатию;
- настройка расстояния между элементами стека;
- настройка максимального количества видимых заметок в свернутом стеке;
- сохранение настроек приложения;
- адаптивный интерфейс для портретного и альбомного режимов;
- локальное хранение данных.

## Архитектура

Проект разделён на три основных слоя:

```text
Presentation
    ↓
Domain
    ↓
Data
```

### Presentation

Presentation-слой содержит:

- `Activity` и `Fragment`;
- `ViewModel`;
- UI-state;
- адаптеры `RecyclerView`;
- кастомные View;
- навигацию;
- экран настроек.

Состояние списка заметок хранится во `ViewModel` и наблюдается UI через `Flow`.

Сбор состояния выполняется lifecycle-aware:

```text
ViewModel
   ↓
StateFlow
   ↓
repeatOnLifecycle
   ↓
Fragment
   ↓
RecyclerView
```

Это позволяет прекращать активный сбор состояния, когда UI не находится в подходящем lifecycle-состоянии.

### Domain

Domain-слой содержит:

- domain-модели;
- интерфейсы репозиториев;
- use case'ы;
- модели настроек приложения.

Presentation-слой работает с данными через domain-контракты и use case'ы, не обращаясь непосредственно к Room или DataStore.

### Data

Data-слой содержит:

- Room DAO;
- Room Entity;
- преобразование Entity в domain-модели;
- реализации репозиториев;
- DataStore для пользовательских настроек.

Поток данных заметок выглядит следующим образом:

```text
Room
   ↓
DAO
   ↓
Repository
   ↓
Flow<List<Note>>
   ↓
Use Case и ViewModel
   ↓
UI State
   ↓
RecyclerView
```

## Кастомный стек заметок

Одна из основных технических частей проекта — собственный компонент `NoteStackView`.

`NoteStackView` реализован как кастомный `ViewGroup`, который самостоятельно управляет размещением дочерних View и отображает несколько заметок в виде стопки.

Стек имеет два состояния:

- свернутое;
- развернутое.

В свернутом состоянии отображается ограниченное количество заметок с визуальным смещением относительно друг друга.

При нажатии стек раскрывается, после чего пользователь может взаимодействовать с отдельными заметками.

Для компонента реализованы callbacks:

- обычное нажатие по заметке — переход к редактированию;
- долгое нажатие — изменение состояния заметки;
- изменение состояния раскрытия стека.

## Анимация стека

Для анимации используются стандартные Android Animation API:

- `ObjectAnimator`;
- `AnimatorSet`;
- `PathInterpolator`.

При раскрытии и сворачивании заметки перемещаются по координатам `translationX` и `translationY`.

Для каждого элемента создаются отдельные `ObjectAnimator`, после чего они объединяются через `AnimatorSet`.

```text
NoteStackView
      ↓
ObjectAnimator X + ObjectAnimator Y
      ↓
AnimatorSet
      ↓
PathInterpolator
      ↓
анимированное положение заметки
```

Для элементов используется последовательная задержка старта, поэтому карточки двигаются не одновременно, а образуют каскадную анимацию.

Для движения применяется cubic Bézier-интерполятор через `PathInterpolator`, благодаря чему раскрытие и сворачивание выглядят более естественно, чем при линейном изменении координат.

Также отдельно обрабатывается анимация элемента управления сворачиванием стека.

## RecyclerView

Основной список реализован через `RecyclerView` и `LinearLayoutManager`.

Список содержит элементы разных типов:

- заголовки дат;
- отдельные важные заметки;
- стеки обычных заметок.

Для обработки разных типов элементов используются отдельные adapter delegates.

Таким образом `RecyclerView` отвечает не только за обычный линейный список, но и за размещение кастомных `NoteStackView`.

## DiffUtil и частичное обновление элементов

Для обновления списка используется `DiffUtil`.

Помимо стандартных:

- `areItemsTheSame`;
- `areContentsTheSame`;

реализован `getChangePayload`.

Особенно это важно для `NoteStackItem`.

Если внутри стека изменилась только одна заметка, при этом:

- идентификатор стека не изменился;
- количество заметок осталось прежним;
- порядок заметок не изменился;

DiffUtil определяет конкретную изменившуюся заметку и передаёт payload с её `id` и новым состоянием.

Схема обновления выглядит так:

```text
старый NoteStackItem
        ↓
DiffUtil
        ↓
найдена одна изменившаяся Note
        ↓
payload
        ↓
обновляется только соответствующая NoteView
```

Это позволяет избежать полной перерисовки всего `NoteStackView`.

Такой подход уменьшает количество лишних обновлений UI и позволяет избежать визуального мерцания стека при изменении одной заметки.

Если структура стека изменилась — например, изменилось количество или порядок заметок — выполняется полное обновление элемента.

## Группировка заметок

Перед отображением заметки преобразуются в набор UI-элементов.

Сначала они сортируются по времени создания, после чего группируются по датам.

В каждой группе:

- важные заметки отображаются отдельно;
- остальные заметки объединяются в стек.

Упрощённо:

```text
List<Note>
    ↓
сортировка по createdAt
    ↓
группировка по дате
    ↓
DateHeader
    ├── ImportantNote
    ├── ImportantNote
    └── NoteStack
          ├── Note
          ├── Note
          └── Note
```

В результате UI получает готовую структуру элементов для `RecyclerView`.

## Адаптивный интерфейс

Для портретного и альбомного режимов используются разные layout-конфигурации.

### Портретный режим

В портретной ориентации пользователь работает с одним экраном за раз:

```text
Список заметок
      ↓
Редактор заметки
```

Переход между экранами выполняется через Jetpack Navigation.

### Альбомный режим

Для альбомной ориентации реализован двухпанельный интерфейс:

```text
┌────────────────────┬────────────────────┐
│                    │                    │
│   Список заметок   │      Редактор      │
│                    │                    │
│                    │                    │
└────────────────────┴────────────────────┘
```

Экран разделяется вертикальной `Guideline`.

В левой половине располагается отдельный `NavHostFragment` со списком заметок, а в правой — контейнер редактора.

Это позволяет использовать дополнительную ширину экрана и не заставляет пользователя постоянно переключаться между списком и редактированием заметки.

## Room

Для постоянного хранения заметок используется **Room**.

Data-слой содержит:

- `NoteDao`;
- Room Entity;
- mapper `Entity ↔ Domain`;
- реализацию `NotesRepository`.

Репозиторий предоставляет поток:

```kotlin
Flow<List<Note>>
```

При изменении данных в Room новое состояние автоматически проходит через repository и ViewModel до UI.

Также через repository реализованы операции:

- получение всех заметок;
- получение заметки по идентификатору;
- добавление заметки;
- добавление списка заметок;
- изменение заметки;
- изменение её состояния.

Room таким образом является постоянным локальным хранилищем заметок.

## Dependency Injection

Для внедрения зависимостей используется **Dagger 2**.

DI-слой содержит:

- components;
- subcomponents;
- modules;
- scopes;
- ViewModel factory.

Через Dagger предоставляются:

- Room database и DAO;
- repository;
- use case'ы;
- ViewModel;
- DataStore;
- другие зависимости приложения.

Для отдельных Fragment используются соответствующие subcomponent factory.

Это позволяет отделить создание зависимостей от их использования и избежать ручного создания инфраструктурных объектов внутри UI.

## Настройки стека

Пользователь может изменять внешний вид стопки заметок:

- расстояние между карточками;
- максимальное количество видимых карточек в свернутом состоянии.

Настройки хранятся через **DataStore Preferences**.

```text
Settings UI
    ↓
SettingsViewModel
    ↓
SettingsRepository
    ↓
DataStore
    ↓
Flow<StackSettings>
    ↓
Notes UI
```

Значения из DataStore преобразуются в `StackSettings` и передаются в список через Flow.

При изменении параметров `NoteStackView` получает новое значение настроек и перестраивает отображение стека.

Настройки сохраняются между запусками приложения.

## Android Views + Jetpack Compose

Основная часть приложения реализована на классическом Android UI:

- XML layouts;
- Fragments;
- RecyclerView;
- custom View и ViewGroup.

При этом экран настроек реализован через **Jetpack Compose** внутри `ComposeView`, размещённого в `BottomSheetDialogFragment`.

Для настроек используются компоненты Material 3, включая `Slider`.

Таким образом проект также демонстрирует возможность постепенного внедрения Compose в существующее View-based приложение без необходимости полностью переписывать UI.

## Поиск

На экране списка реализован `SearchView`.

Изменение поисковой строки передаётся во ViewModel, а отфильтрованный набор элементов возвращается обратно через UI-state.

Текущий поисковый запрос хранится в состоянии ViewModel, поэтому UI отображает актуальное значение после повторного создания View.

## Lifecycle-aware работа с состоянием

UI-state списка наблюдается внутри:

```kotlin
repeatOnLifecycle(Lifecycle.State.STARTED)
```

Состояние собирается только тогда, когда Fragment находится как минимум в состоянии `STARTED`.

Через один UI-state экран получает:

- список элементов;
- поисковый запрос;
- настройки стеков;
- состояние первоначальной загрузки;
- информацию о раскрытых стеках.

После получения нового состояния данные передаются в адаптер через `submitList`.
